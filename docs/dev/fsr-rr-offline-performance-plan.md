# FSR-RR → SR → NR 离线排查与优化执行计划

日期：2026-10-30。状态：待实施；本文不代表测试程序、计时修复或性能优化已完成。

## 目标与范围

用产品实际执行路径查清移植 FSR-RR 的转换、滤波、RR、SR、NR 及提交等待成本，减少反复进游戏调参。最终回答两个问题：移植路径自身的成本在哪里；RR 前序工作是否通过输入、排队或同步影响后续 NR。

离线 GPU 测试使用 RX 9070 XT，不启动游戏。CPU 合约与统计测试不需要显卡。游戏原生 AMD RR 的完整路径不在本项目内；离线结果不能单独证明它比伪装 NVIDIA RR 路径快的原因，仍需最后一组受控游戏采集。

本计划只评估产品桥接、执行组合和调度成本，遵循 [测量纪律](../measurement.md)。NR 网络内部读数用于解释同一产品管线的分段结果，不另建网络排名或修改上游网络基准。模型、pass 数和画质条件不同的结果分开报告。

## 执行顺序与交付物

| 步骤 | 工作 | 交付物与通过条件 |
|---|---|---|
| P0 | 固定基线、检查前置条件 | 可复现 manifest、执行图；确定产品配置与资源输入 |
| P1 | 修复/验证计时归属与统计 | CPU 定向回归通过；拒绝错帧、重复和未完成样本 |
| P2 | 建立最小产品离线链 | 真 RR→SR、可选 NR 跑通；实际提交和回收可追踪 |
| P3 | 完成分段计时与正确性检查 | GPU 与 CPU 窗口可解释；debug 验证及计时干扰检查通过 |
| P4 | 跑基线矩阵，定位瓶颈 | 原始样本、统计、证据与待验证推论；先不优化 |
| P5 | 逐项优化并回归 | 一次一个变量；收益超过噪声且正确性、画质不过退 |
| P6 | 少量游戏采集与真实序列回放 | 验证外部有效性，明确原生与移植差异仍有哪些未知 |

依赖顺序为 P0→P1→P2→P3→P4→P5→P6。P6 的真实输入采集可在 P4 后提前一次，以便 P5 使用；不要求每次候选修改都进游戏。任何阶段发现计时或生命周期错误，先修复并重新建立受影响的基线，再继续优化。

### P0：固定基线与执行图（较低复杂度）

1. 记录当前 commit、未提交产品改动、构建脚本/参数、编译器版本、宿主/runtime/provider/shader/模型的 SHA256；无真实 provider 或资产时明确标为阻塞，禁止用 stub 性能替代。
2. 画出当前启用配置下的真实顺序：转换→RR→合成→SR，以及 NR 实际插入位置。以源码为准核对 `RunBeforeSR`、`ApplyAfterRR` 等配置，不预设 NR 总在 SR 后，也不让离线程序额外执行一次 NR。
3. 固定 GPU adapter/LUID、驱动、OS、HAGS、显示/电源条件、模型/pass、曝光、色彩空间、渲染/输出尺寸、资源格式、队列与在途帧数。初始用一个已知受支持的配置跑通。
4. 审查可复用边界：优先调用产品特性；必要时提取最小公共适配层。禁止复制一份转换/滤波 shader 或重写调度以获得更理想的测试路径。

通过条件：执行图能对应具体产品函数，输入与配置可重建，所有二进制来源可核对。记录缺失项，不因源码存在就声称链路可运行。

### P1：计时与统计先修正（较低至中等复杂度；Bug 修复阶段）

1. 审计 runtime 已完成样本到宿主日志的传递。定义并保留 `run_id`、`segment_id`、产品帧号、录制代次、提交 ID、队列 ID、runtime accepted sample serial 与完成 fence。不同 ID 的关系可以一对多，不能默认相等。
2. runtime 的“最后一个已完成样本”只能在 serial 变化时计入一次；取不到帧号映射时只报独立样本分布，不能挂到当前 Evaluate 帧。异步到达、缺失与重复样本分别计数。
3. 统计按明确的配置切换标记分段，区分普通 FSR、真实 RR、NR 开/关、失败/跳过与初始化。保留原始日志，解析器输出来源文件哈希、行号/记录 ID、时间范围和排除原因；不按文件名猜测窗口。
4. 增加定向 CPU 用例：延迟两帧完成、serial 重复/跳变、切换后旧样本到达、无有效查询、时间戳回绕、录制 reset/重放、提交失败与截断日志。伪数据预先写明应得到的计数和分位数。
5. 区分 CPU 墙钟窗口、GPU 执行窗口和 runtime 网络/其它窗口。已有 `gpu_core_ms` 等历史标签先核对来源及公式，不能从名称推断它只包含神经网络，也不能拿两个不同帧的数相减。

通过条件：每个进入统计的样本可追溯且不会重复计数；无法对齐的历史数据明确降级为分布证据。若修改计时语义，升级结果 schema 并标注旧数据不可直接对比。

### P2：最小离线执行器（中等复杂度；补测试设施）

计划新增 `tests/fsr-rr/`，由该领域的 `run.cmd` 统一进入 CPU、GPU 正确性和显式性能模式；这些是拟建入口，当前不可直接运行。新分析工具若需要独立存在，放 `tools/diag/` 并登记工具索引。

1. 创建设备和产品使用的队列，加载真实匹配版本 provider/runtime；构造产品所需 NGX 参数、颜色、depth、MV、法线/粗糙度、反照率及矩阵。区分必需和可选 guides，不用全零输入掩盖无效参数。
2. 首先执行 RR→SR，确认 API 返回成功、实际 dispatch、输出有效且不是回退。随后接入产品已有 NR 接缝，验证运行零次或恰好一次；记录最终生效配置。
3. 合成输入至少包含平面、边缘、暗部、高光、运动与遮挡变化。连续序列提供一致的 jitter、曝光、矩阵、MV 与 reset；预热历史，不用不断 reset 的单张图代表时域稳态。
4. 保留产品 barrier、跨 API 共享、提交钩子、Signal/Wait 和退休票据。测试程序负责 GPU 提交后真正通知产品追踪路径，不能通过“每帧等 GPU 空闲”绕过环槽压力和生命周期问题。
5. 分开两个模式：串行诊断模式帮助定位每段成本；受控在途帧数模式观察真实吞吐和排队。两者单独输出，不互称产品性能。
6. 先覆盖默认格式/尺寸，再覆盖不整除线程组的尺寸、资源 resize、历史 reset、RR/NR 开关、特性重建、提交失败、销毁时仍有在途工作。

通过条件：成功路径有实际执行证据；失败路径清楚报告而非静默回退；未完成资源不复用、不超时强退。所有长期测试接入领域入口，重型性能模式不混入默认无 GPU CI。

### P3：分段计时与校准（中等复杂度）

| 窗口 | 测量方式与含义 |
|---|---|
| FloorSeed、每级 FloorFilter、InputConv | 同队列 GPU timestamp；记录本帧实际 pass 数，未执行项标记 skipped |
| RR dispatch、OutputComp、SR | 对真实产品录制边界打点；包含边界内实际命令，不能拿 CPU dispatch 调用耗时代替 |
| NR 输入捕获/转换、输出回写 | DX12 GPU timestamp，区分 copy、compute 和资源交接 |
| NR network/other | 使用 runtime 已完成的同一个样本；记录后端计时域与包含范围 |
| CPU 录制、提交、等待、输入就绪→输出可用 | QPC + 提交/fence 事件；窗口定义和起止 ID 随样本保存 |
| 整链吞吐与输出就绪延迟 | 稳态完成帧数/有效墙钟窗口；另报逐帧延迟，不能将吞吐倒数当作延迟 |

1. 使用查询/读回环，fence 完成后异步读取；查询槽和 CBV 一样按实际退休回收。采样区间不插入逐段 CPU 等待，测试末尾 drain 单独记录，不混入稳态。
2. 每个队列使用自己的 timestamp frequency。跨队列绝对时间对齐需可靠时钟校准和误差说明；DX12 与 Vulkan/HIP 等后端时间域不能直接相减。不能校准时只报各域时长和同步依赖。
3. RR、SR、NR 可能重叠，分段时长相加不一定等于墙钟总窗。只对同队列、互不重叠且范围完整的区间做闭合校验；余差单列为未归因，不能自动算作 RR。
4. 用同一输入序列交错比较计时开/关，估算查询和日志开销。正式性能模式关闭 debug layer/GPU validation、逐帧文本和读回；另跑正确性模式并检查 D3D12 消息及 device removal。

通过条件：各窗口公式、包含的等待和时钟域写进结果说明；有效样本、丢弃原因、查询溢出可见。检测到计时干扰明显时降低采样密度，并保留采样策略。

### P4：基线矩阵与归因（中等复杂度；测性能阶段）

先跑小矩阵，再按瓶颈扩展，避免一开始全排列。

| 模式 | 用途与比较限制 |
|---|---|
| 普通 SR，NR 关 / 开 | NR 桥接参考与 RR 关闭路径成本；明确两者实际 NR 输入尺寸 |
| 移植 RR→SR，NR 关 | RR 管线完整成本，不能用它减普通 SR 就声称得到纯 denoiser 时间 |
| 移植 RR→SR，NR 在受支持的 SR 前/后接缝 | 比较输入尺寸、内容和调度；每种接缝独立成组 |
| 相同 NR 输入纹理的独立重放 | 固定内容/尺寸后观察 NR 稳态成本；作为隔离实验，不冒充游戏总路径 |
| 同一条在途 RR 链，切断前序负载后再跑 NR 的诊断模式 | 判断排队影响；必须与正常链并列，额外同步导致的变化单独说明 |

默认配置确认后，至少增加 1280×720→3840×2160 和一个更高渲染尺寸的受支持组合；不得通过降低 NR 分辨率获得“RR 优化”结论。格式、模型/pass、NR 接缝、inline/split 等每轮只变一项，且只测产品真实支持的组合。

正式测量协议：

1. 一人/一个执行器调度 GPU；启动前和运行期间检查游戏及其它 GPU 负载。发生冲突只停止自有 benchmark，保留结果并标为无效，不结束游戏。
2. 将 shader/模型编译、加载与首次分配列为冷启动项；稳态预热至少 120 帧并确认构建结束、历史和频率趋稳。随后每项至少 600 个有效帧且持续至少 30 秒；未趋稳则延长并记录原因。
3. 同进程/会话按 A/B/B/A 交错，至少 3 轮；切换时 reset 并重新预热。在途帧数固定，之后再单独测扩展的帧数，不混用。
4. 输出计数、有效时长、median、P90/P95/P99、mean、轮间差异和每轮原始分布；FPS 来自完成帧数/墙钟，不平均瞬时 FPS。时长降低率为 `(baseline-candidate)/baseline`，吞吐比另算。
5. 保留慢帧；失败、TDR、编译、配置切换按预先定义规则标注，禁止为好看事后裁剪。A/A 重复建立噪声带，优化验收阈值以该噪声带和实际收益目标决定，不预先承诺固定帧数。

归因时分三种证据：同输入 NR network 变慢指向执行/竞争因素；network 不变而输入就绪→输出可用变长指向传输、等待或排队；只有整体帧率不同仍不足以归因。每种推论必须附可推翻它的下一项实验。

### P5：按瓶颈优化（中等至较高复杂度；先修 Bug 再优化）

按 P4 的实测占比排序，以下只是候选，不预设都有问题：

| 条件 | 优先动作 | 必须验证 |
|---|---|---|
| 计时、状态、提交或退休错误 | 先修帧归属、重复调用、无效等待和资源生命周期 | 定向回归；受影响结果重新采集，不能以加速掩盖错误 |
| CPU 提交/同步占比高 | 排除冗余锁、查询、Signal 和重复状态查询；保留有在途 RR 时的回收 | RR 从未开启、运行中关闭、仍有在途票据、并发队列 |
| NR 复制/转换显著 | 优先评估现有产品支持的共享资源、格式和输出路径，减少多余往返 | 格式/颜色空间一致、资源所有权、跨队列同步与失败恢复 |
| FloorFilter 成本高 | 先确认每级必要性，评估跳过无效 pass、减少级数、采样或融合 | 原始基线保留；薄几何、暗部、高光、运动、遮挡边缘与时域闪烁 |
| InputConv/OutputComp 成本高 | 评估重复采样、带宽和可合并操作 | UAV/barrier、数值精度、guide 与曝光语义一致 |
| RR/SR 内部成本高 | 检查实际生效模式、输入尺寸、重建与冗余调度 | 只能归因黑盒外部可见区间；不能声称已优化未知内部算法 |

每个候选单独提交，附相同 manifest 条件下的 A/B 与输出对比。优先不改变画质的冗余消除，再做有画质取舍的实验。减少滤波、改精度和融合 pass 的合成输入结果只能作性能与初步正确性证据；进入产品默认前必须经过真实连续序列和游戏验证。

验收同时满足：收益在重复轮次中稳定且超过 A/A 噪声；总链没有被某段局部加速拖慢；正确性检查通过；RR 关闭和 NR 关闭路径无可检测回退。诊断计时默认关闭，避免长期给普通路径增加额外开销。

### P6：受控游戏采集与回放闭环（中等复杂度）

1. 同一游戏版本、存档、站位/路线、渲染与输出尺寸、RR 质量、NR 模型/pass、FG 与帧率限制，分别确认“游戏原生 AMD RR”和“伪装 NVIDIA 入口→移植 FSR-RR”真正生效，记录 provider、配置和切换标记。
2. 允许热切换时采用同会话交错窗口；必须重启时做多轮配对并声明会话混杂，不能把不同会话直接当作严格 A/B。FG 初始关闭以隔离应用帧，必要的 FG 测试另开组并记录帧类型。
3. PresentMon 用于应用/显示节奏；RR/NR 组件归因依靠产品 timestamp 或可取得的 GPU capture。原生 RR 无法获得准确边界时只报告整体差值和该未知项。
4. 若可采集真实输入，保存连续帧颜色、完整 guides、格式、矩阵、jitter、曝光、MV 单位、reset/历史、资源状态与配置。缺关键字段的序列不能作为等价回放证据。
5. 输入导出与磁盘写入使用独立采集轮次，不与正式计时混用；导出完成后校验帧号、哈希和资源内容，不能因为文件存在就认为采集成功。
6. 回放先验证同一序列的确定性/允许数值误差及历史预热，再比较候选。最终只将 P5 中最有证据的候选带回游戏，检查运动画质、稳定性及实际收益。

完成条件：能解释移植路径主要成本和 NR 受影响的方式；原生路径不能观测的部分明确列为未知，不要求凭不完整数据强行解释所有帧率差。

## 结果、报告与完成标准

每次执行的结果目录至少包含：

- `manifest.json`：schema、来源 commit/dirty diff 摘要、构建配方、实际二进制/资产哈希、设备与有效配置、输入序列哈希、预热/采样/在途帧数。
- `frames.csv`：帧/录制/提交/样本映射、阶段起止与时长、计时域、完成状态、失败/跳过原因。缺值用缺值表示，不能写成零耗时。
- `events.jsonl`：切换、reset、创建/销毁、提交/fence、编译与异常事件；保留未经重写的原始日志。
- `summary.json` 与人工报告：每轮统计、配对范围、噪声、无效样本数量、结论和下一项实验。

可再生构建与结果放 `exports/`，游戏采集按 [工作区规范](../workspace.md) 存放；真实输入与模型由显式参数提供并校验，不把本机材料当作 tracked 测试依赖。仓库只提交程序、schema、可公开的小型合成 fixture 与稳定结论，公开报告不得链接本机调查文件。

报告每条判断分为：**直接证据**（同输入、同窗口、同配置可复现）、**有条件推论**（列出假设及反证实验）、**未知**（写明缺哪个边界/样本）。历史日志可以先做独立复核，但不替代本计划的新基线。

首个可用里程碑为 P0–P3：可信计时 + 最小完整链，暂不做 shader 优化。第二里程碑为 P4：明确首要瓶颈。第三里程碑为 P5–P6：至少一个候选完成性能与真实画质闭环，或给出有证据的不修改结论。

本文制定计划不触发编译、GPU 运行、出包或发布；实施时逐阶段审查和验证，发布仍遵循 [唯一发布流程](../release.md)。
